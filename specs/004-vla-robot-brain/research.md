# Research Phase 0: Vision-Language-Action (VLA) Module

## Decision: Whisper Model Integration with ROS 2

-   **Rationale**: Leveraging `ros-ai/ros2_whisper` provides an optimized, existing solution for real-time speech-to-text transcription within the ROS 2 ecosystem. This package handles the audio capture (using `pyaudio`) and integrates `whisper.cpp` for efficient inference, making it suitable for quick integration into a humanoid robot's perception pipeline. This allows for direct processing of spoken commands into text, which can then be fed into an LLM or action mapping.
-   **Alternatives considered**:
    -   *Custom Whisper integration*: Would require significant effort for audio capture, Whisper model loading, and efficient inference within a ROS 2 node, duplicating existing work.
    -   *Cloud-based speech-to-text APIs*: Introduces latency and dependency on external services, which might not be ideal for real-time robotic control and local experimentation.

## Decision: LLM Integration Patterns for Robotic Planning

-   **Rationale**: To enable complex cognitive planning, the LLM will be integrated as a high-level task planner. This involves:
    1.  **High-Level Task Decomposition**: LLMs interpret abstract natural language commands and break them down into a sequence of lower-level, executable robot actions.
    2.  **Semantic Planning and Reasoning**: The LLM provides common-sense knowledge to understand task context, object properties, and logical action flows.
    3.  **Natural Language Interface**: The LLM facilitates intuitive human-robot interaction by translating commands into a robot-understandable format.
    4.  **Integration with Perception**: LLMs can utilize information from the robot's perception system (from Module 3) to inform their planning.
-   **Alternatives considered**:
    -   *Rule-based AI*: Lacks flexibility and scalability for complex, open-ended natural language tasks.
    -   *Traditional symbolic planners (e.g., PDDL without LLM)*: Requires explicit domain knowledge representation and struggles with natural language ambiguity.

## Decision: ROS 2 Interfaces for Humanoid Robot Actions

-   **Rationale**: ROS 2 `actions` are the most suitable interface for managing complex, long-duration humanoid robot behaviors (e.g., walking, grasping, multi-step tasks). Actions provide asynchronous communication, continuous feedback on progress, and support preemption/cancellation, which is critical for robust robotic control. `ros2_control` will be used for low-level joint control, and `MoveIt2` for motion planning, integrating with the LLM's high-level plans. Whole Body Control (WBC) is a fundamental underlying concept that guides the execution of these actions while maintaining balance.
-   **Alternatives considered**:
    -   *ROS 2 `messages` for all actions*: Too simplistic for long-duration tasks, lacks feedback and preemption.
    -   *ROS 2 `services` for all actions*: Synchronous nature makes it less suitable for tasks requiring continuous progress updates.

## Decision: Docusaurus Best Practices for Multi-Chapter Modules

-   **Rationale**: For optimal content organization and user experience in complex, multi-chapter modules like VLA, Docusaurus best practices will be followed:
    -   **Subfolders in `docs/`**: Each module will have its own subfolder (e.g., `docs/module-4/`).
    -   **`sidebars.js` Configuration**: Utilize `type: 'autogenerated'` within a custom category for Module 4 in `sidebars.js` to automatically structure the navigation based on file organization.
    -   **Front Matter**: Each Markdown file will include front matter (`id`, `title`, `sidebar_label`, `sidebar_position`) for precise control over metadata and ordering.
    -   **Internal Linking**: Use `@doc` linking conventions for robust internal navigation within and between chapters.
    -   **Code Snippets**: Employ fenced code blocks with language highlighting, titles, and line highlighting (`// highlight-next-line`) to enhance readability and clarity of code examples.
-   **Alternatives considered**:
    -   *Flat file structure*: Leads to unmanageable navigation and poor user experience for complex modules.
    -   *Manual sidebar entries for every page*: High maintenance overhead and prone to errors.
